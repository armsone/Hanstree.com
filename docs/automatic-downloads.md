# 홈페이지 배포 정보 자동화

## 범위와 완료 기준
제품 설명·기능·스크린샷·개인정보 안내는 홈페이지에서 관리한다. 공개 다운로드, 제품 버전, 게시일, 파일 크기는 GitHub 릴리스에서 가져온다. 단순 버전업에 홈페이지 변경·커밋·배포가 없어야 한다. 실제 릴리스의 공개가 발동 조건이며, 로컬 빌드와 비공개 초안은 반영하지 않는다.

## 기존 제품 릴리스
1. 기존 제품 작업 폴더에서 빌드·서명·필수 무결성 확인을 끝낸다.
2. 최종 파일을 GitHub 릴리스 자산으로 올린다. 기존 버전 포함 파일명을 유지한다.
3. 가능하면 아래 도구로 `release.json`도 만들어 같은 릴리스에 올린다. 버전·빌드·Android 내부 코드는 기존 빌드 과정의 실제 값을 전달한다. 이 도구는 파일명·크기·해시를 계산하며 서명이나 앱 내부 버전을 검증하는 도구가 아니다.
4. 모든 파일과 정보를 준비한 후 릴리스를 공개한다. 게시 후 바뀐 파일로 메타데이터를 재사용하지 않는다.
5. 제품 화면에서 표시 버전과 다운로드 파일이 일치하는지 확인한다. 홈페이지의 `data.ts`와 `fallbackUrl`은 버전업만으로 수정하지 않는다.

```sh
node /Users/armsone/git/NasFinder.com/build/release-metadata.mjs \
  --version 2.6.2 --build 202610141300 --version-code 412000 \
  --artifact NasFinder-Android=/absolute/path/NasFinder-Android-2.6.2.apk \
  --minimum-os 'Android 8.0+' --output /absolute/path/release.json
```
위 숫자와 경로는 실행 예시다. 실제 패키징 값으로 대체한다. 한 릴리스에 여러 다운로드가 있으면 `--artifact`를 반복한다. 전체 자산의 제품 버전이 다르면 릴리스를 분리한다.

## 자동 반영과 장애 처리
- 제품마다 D1의 `release_snapshots`에서 마지막 정상 정보를 보관한다. 최초 한 번만 기존 공개 주소를 초기값으로 사용한다.
- 확인 성공 후 5분 동안 재사용하며, 그 이후 첫 요청이 갱신한다. 갱신은 동시 요청 중 하나만 수행한다. 홈페이지를 방문하지 않을 때에는 조회하지 않는다.
- 조회 실패 시 마지막 정보를 유지하고 ‘마지막 확인 정보’로 표시한다. 1분 뒤 요청부터 재시도한다. 성공 시 다시 자동 반영된다.
- `release.json`이 없는 기존 릴리스도 지원한다. 버전은 태그/파일명, 크기·게시일은 GitHub 값을 사용한다. 알 수 없는 빌드·내부 코드는 ‘미제공’으로 표시한다.
- 배포 기록이 있으면 표시한 릴리스 ID를 다운로드 버튼에 붙인다. 그 뒤 다른 버전이 공개돼도 해당 화면에서 표시한 파일을 받는다. 선택한 릴리스가 사라졌다면 다른 버전으로 바꾸지 않고 재확인을 안내한다.
- 여러 파일이 같은 선택 조건에 맞으면 임의 선택하지 않는다. 필요하면 제품별 파일명 조건을 명확하게 한다.

## 채널과 저장소
`app/releases.ts`는 제품을 처음 등록하거나 플랫폼/저장소/파일명 규칙을 바꿀 때만 수정한다. 기본은 공개 정식 릴리스이며 초안·시험판을 제외한다. 한 저장소에 여러 제품이 있으면 제품별 태그/파일명으로 구분한다.

바로보기 Windows 시험판은 공개 홈페이지 저장소 `armsone/Hanstree.com`의 `windows-v버전` 시험 릴리스에 Chrome·Whale ZIP과 `release.json`을 게시한다. 홈페이지의 고정 주소와 QR은 유지한다. 기존 홈페이지 내 ZIP은 이전 링크 호환을 위해 남겨 둔다. 새 ZIP은 홈페이지 저장소의 소스 파일에 추가하지 않는다.

NasOS 서버 설정은 `v` 태그 릴리스 페이지, 한스트리 마을은 `village-v` 태그의 mcpack을 각각 선택한다. 소스 릴리스와 설치 파일을 서로 바꾸지 않는다.

한양 Swift는 `swift-v버전` 태그를 사용한다. 기존 `v0.3.0`만 이전 공개판으로 인정하며, JVM 릴리스와 섞이지 않게 한다. Kotlin/JVM은 JAR 자산으로 별도 선택한다.

## 반영되지 않는 항목
새 기능 설명·스크린샷·법적 고지·지원 정책은 확인 후 별도로 수정한다. TestFlight는 승인·공개 상태가 별도로 필요하므로 이 GitHub 자동화의 대상이 아니다. 새 제품 등록과 파일명/플랫폼 구조 변경에는 홈페이지의 초기 등록이 필요하다.


## 기존 공개 릴리즈 정보 보완

`build/sync-release-metadata.mjs`는 현재 등록된 공개 릴리즈의 자산 사실과 기존 릴리즈 본문으로 배포 정보를 보완한다. 기본 실행은 읽기 전용이며 `--publish`를 명시한 경우에만 없는 `release.json`을 추가한다. 기존 파일·메타데이터를 덮어쓰지 않으며 내용 충돌이나 수정 불가능한 릴리즈는 별도로 보고한다. 이미 `release.json`이 있는 경우 실제 자산과 일치하는지 확인한다.

```sh
node build/sync-release-metadata.mjs --repo=NasFinder-Android
node build/sync-release-metadata.mjs --repo=NasFinder-Android --publish
```

이 도구는 기존 공개판을 보완하는 용도다. 새로운 릴리즈는 빌드 직후 최종 파일로 `release-metadata.mjs`를 실행하여 초안에 패키지·메타데이터를 먼저 올리고, 업로드 확인 후 공개한다. 공통 릴리즈 스킬과 각 앱의 릴리즈 안내도 이 절차를 따른다. 이번 전환의 확인 결과는 [릴리즈 정보 반영 기록](release-metadata-transition.md)에 남겼다.
